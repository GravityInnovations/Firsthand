Implementation guide

Add a better problem-reporting flow to your product.

Firsthand has three independent pieces. Add the recorder to your product, run the transcoder to prepare an editable report, then run the reporter to store approved evidence and create GitHub issues.

Start here

What you need

Node.js 20 or newer, a place to run two Node services, and a GitHub repository if you want Firsthand to create issues. The recorder itself runs in the browser, but the credentials must stay on your server.

The important boundary: the browser sends evidence to your own trusted routes. Those routes call the transcoder and reporter. Do not put OpenAI, storage or GitHub keys in frontend code.

1. Start the backends

Run the transcoder and reporter separately.

Clone the repository, then install and start each service in its own process.

cd transcoder
npm install
# set TRANSFORMER_API_KEY in the server environment
npm run dev

cd ../reporter
npm install
# set reporter, storage and GitHub settings in the server environment
npm run dev

The transcoder listens on http://127.0.0.1:4100 locally. The reporter listens on http://127.0.0.1:4200.

2. Add the recorder

Mount one small browser component.

Build the recorder package locally or install it once it is published. Import its stylesheet from your application’s global style entry, then mount it inside a browser client component.

import "@gravityinnovations/firsthand-recorder/styles.css";
import { createRecorder } from "@gravityinnovations/firsthand-recorder";

const recorder = createRecorder({
  position: "bottom-right",
  reporter: { userIdentifier: currentUser.id },
  transcoder: { endpoint: "/api/firsthand/prepare" },
  submission: { endpoint: "/api/firsthand/reports" },
  metadata: { application: "customer-portal" }
});

The recorder requires a secure browser context: HTTPS in production or localhost while developing. The browser always asks the user which screen, window or tab to share.

3. Keep credentials on the server

Proxy browser requests through your application.

Create two server-side routes. The first forwards the recorder’s multipart evidence to the transcoder. The second forwards the reviewed prepared report and original recording to the reporter using the reporter’s Basic-auth client credentials.

  • Prepare route: browser → your server → transcoder POST /v1/prepare
  • Submit route: browser → your server → reporter POST /v1/issues

The repository’s tests/nextjs example shows these two routes using a Next.js App Router integration. The static tests/html example shows the same shape without a framework.

4. Configure issue creation

Give the reporter storage and GitHub access.

For a local test, host storage is enough. In production, choose the storage provider that fits your infrastructure: host, FTP, S3, R2 or an HTTP upload service that returns a URL.

REPORTER_CLIENT_ID=your-server-client-id
REPORTER_CLIENT_SECRET=a-long-random-secret
STORAGE_PROVIDERS=host
STORAGE_HOST_ROOT_PATH=.evidence
STORAGE_HOST_PUBLIC_BASE_URL=https://reporter.example.com/v1/evidence-files

GITHUB_ENABLED=true
GITHUB_AUTH_MODE=token
GITHUB_OWNER=GravityInnovations
GITHUB_REPOSITORY=Firsthand
GITHUB_TOKEN=server-side-fine-grained-token

REPORTER_INITIAL_STATUS=submitted
REPORTER_INITIAL_STATUS_LABEL=Developer review required

Use a fine-grained GitHub token limited to the chosen repository with Issues: read and write. Keep it in your deployment environment, never in a browser bundle or committed file.

The API surface

The endpoints your server uses.

ServiceEndpointPurpose
TranscoderPOST /v1/prepareCreates an editable report from description, metadata and media.
ReporterPOST /v1/issuesStores approved evidence and creates the mapped GitHub issue.
ReporterGET /v1/users/:userIdentifier/issuesReturns the issues for one of your system users.
ReporterGET /v1/issues/:reportId/commentsReturns refreshed GitHub comments for that mapped issue.
ReporterPOST /v1/issues/:reportId/commentsAdds a user reply to the mapped GitHub issue.

Then make it yours

Start locally. Change only what you need.

Use the HTML test first to verify recording, report preparation and issue creation. Then copy the Next.js route pattern into your product. The recorder theme, labels, capture settings and metadata are all configurable without changing the service boundaries.
